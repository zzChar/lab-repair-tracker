# Epic 3 Context: 验收与关闭

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让报修人在试打后对原工单作出明确的验收决定。试打正常时确认关闭，仍有故障时说明原因并退回原负责人，直至复测成功。即使同一验收轮收到冲突请求或写入失败，工单状态和处理历史也应一致。

## Stories

- Story 3.1: 试打成功后关闭
- Story 3.2: 试打失败后退回原负责人
- Story 3.3: 保护同一轮验收的唯一结果
- Story 3.4: 隔离旧请求与写入失败

## Requirements & Constraints

- 只有该单报修人可确认关闭或退回「待确认」工单。关闭进入「已关闭」。退回必须填写包含非空白字符的原因，工单回到「处理中」，保持原编号和原负责人。
- 原负责人可从原工单查看退回原因和已记录的处理历史，然后继续追加进度并再次提交验收。详情按版本展示历史，保留各轮处理结果、退回原因和成功关闭事件。
- 同一轮验收只允许一个结果。关闭和有效退回同时提交时，恰好一次写入成功。失败请求不能改动状态、跟进人、版本、更新时间或事件记录。之前验收轮的页面即使看到相同状态，也不能作用于新一轮。
- 验收测试覆盖试打成功直接关闭和失败退回后复测关闭。权限验证直接访问服务端，越权请求不能改变工单和历史。

## Technical Decisions

- Django 从登录会话确定操作人，工单服务按身份、归属及状态执行授权。状态操作经同一写入边界处理。工单详情按可见性规则查询。
- SQLite 使用短 `IMMEDIATE` 写事务。按工单编号、预期状态和页面读取时的版本做条件更新。写入成功后版本加一，未命中条件时返回冲突并提示刷新。锁等待超时单独报告为暂时不可用。
- 工单摘要和对应事件必须同事务提交或回滚。事件记录工单版本、操作者、动作及服务端时间。进度、处理结果和退回原因保存在各自事件中。工单最近更新时间与最新进度事件时间分别展示。
- 并发验证使用同一个本地数据库文件的两个独立连接及两个报修人会话，分别覆盖关闭和退回胜出。另验旧版本、历史写入失败回滚和数据库锁等待超时。重新读取数据库断言最终状态与事件一致。

## UX & Interaction Patterns

- 跟进人提交处理结果后，报修人在工单详情核对结果、试打并选择确认关闭或填写原因退回。退回原因在原工单详情中对原负责人可见。
- 旧页面冲突时提示刷新再操作。锁等待超时时提示暂时无法处理。处理历史可用于核对复测前后的处理过程。

## Cross-Story Dependencies

验收阶段依赖史诗 2 提供的跟进人、处理进度及提交验收功能。关闭和退回共享同一状态及版本规则，并发与写入失败验证覆盖两条操作路径。
