# Epic 1 Context: 报修与查询

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让单个实验室的成员用自己的账号提交公共设备故障，并从个人列表找回原工单。以公共打印机卡纸为演示场景，报修人在负责人接单之前就能核对设备、故障和当前状态。后续处理与验收阶段沿用同一工单及报修人身份。

## Stories

- Story 1.1: 从 Django 骨架启动并登录
- Story 1.2: 提交公共设备报修
- Story 1.3: 查找我提交的工单
- Story 1.4: 查看单张工单及保护详情入口

## Requirements & Constraints

- 普通成员和负责人分别使用自己的演示账号。服务端从 Django 会话取得当前用户，通过负责人组判断角色。未登录访问受保护入口会得到登录提示或被重定向。
- 提交报修需要设备名称、位置和故障描述。成功后创建待接单工单，将当前会话用户记为报修人，初始跟进人为空。
- 报修人从自己的列表查找工单。列表展示设备、状态、跟进人和工单最近更新时间。详情还展示工单编号、位置和故障描述，后续史诗随处理动作补齐进度和验收历史。
- 列表和详情共用服务端可见性规则。无关成员知道工单编号时，直接请求详情也拿不到工单数据。负责人查看待接单工单和自己接下的工单的能力随接单阶段交付。

## Technical Decisions

- 以 Django 官方 `startproject` 为起点，使用服务端模板、表单、会话和用户组。候选基线为 Python 3.12 与 Django 5.2 LTS，项目上下文建议 Django 5.2.19。记录实际使用的依赖版本，以及评审机的运行和初始化步骤。
- 应用使用单机 SQLite 文件数据库。新建和后续工单变更通过统一写入服务，在短事务内同时写入工单和事件。页面渲染在事务外完成。查询通过统一查询服务。
- 登录基础只准备认证、会话和演示账号所需的数据结构。首个工单写入能力引入工单与事件结构。工单使用服务端时间，事件保留操作者和动作，成功提交后才报告操作成功。
- 工单最近更新时间表示最近一次成功写入。后续展示的最新进度时间取自进度事件，避免将接单或验收时间误认成进度更新时间。

## UX & Interaction Patterns

从登录页进入受保护的应用入口。提交后，报修人可从自己的工单列表进入详情核对信息。待接单工单的跟进人显示「尚无跟进人」，无权访问的详情响应不返回工单字段。

## Cross-Story Dependencies

1.1 提供会话身份与角色判断，1.2 在此基础上创建工单，1.3 和 1.4 分别交付本人列表和详情。史诗 1 可在尚未接单时独立验收，史诗 2 使用已创建的待接单工单继续推进。
