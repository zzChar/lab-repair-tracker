# Epic 2 Context: 接单与跟进

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

负责人从待接单列表找到工单，接下后在自己的列表中持续跟进，记录进度并提交处理结果。报修人能看到谁在跟进、最新进展和对应时间，设备处理完成后按同一张工单验收。

## Stories

- Story 2.1: 查看待接单和本人接下的工单
- Story 2.2: 接下待接单工单
- Story 2.3: 追加处理进度
- Story 2.4: 填写结果并提交验收

## Requirements & Constraints

- 负责人分别查看待接单工单和自己接下的工单。两个列表均显示设备、状态、跟进人和工单最近更新时间。报修人保留查看自己提交的工单的权限。
- 列表和详情使用一致的服务端授权。负责人可以查看待接单和自己接下的工单详情。对由他人报修、他人接下的工单，直接请求也得不到详情数据。每次写入按当前身份、归属及状态校验资格。
- 接单后工单由「待接单」进入「处理中」，记录当前负责人。只有跟进人可以为「处理中」的工单追加进度或提交处理结果。进度可多次追加，处理结果提交后进入「待确认」。
- 进度历史按工单版本展示，保留每条进度的内容和记录时间。工单最近更新时间来自最后一次成功变更。最新进度时间取自最新一条进度事件，提交验收后仍可查之前的进度。

## Technical Decisions

- 使用 Django 服务端页面和表单。页面调用统一工单查询与写入服务。从登录会话和负责人组得出身份与角色，按报修人、跟进人和状态决定访问范围。
- 使用本机 SQLite 文件和显式的短 IMMEDIATE 写事务。页面渲染在事务外完成。锁等待超时返回暂时不可用，条件更新未命中返回冲突并提示刷新。
- 所有既有工单的写入携带读取时的版本。在事务中检查工单编号、预期状态和版本，成功时版本加一。接单冲突和权限拒绝不改变原工单。
- 工单摘要与新增事件同一事务提交或回滚。事件记录工单版本、操作者、动作和服务端时间，进度与处理结果保存到对应事件。成功提交后才返回操作成功。

## UX & Interaction Patterns

负责人在待接单列表找任务，在本人接下的列表继续处理。报修人从自己的工单详情查看跟进人、最新进度及其记录时间。提交处理结果后，工单显示「待确认」，报修人可据此开始验收。

## Cross-Story Dependencies

本史诗依赖已提交的待接单工单和受保护的详情入口。负责人列表先于接单，接单后可追加进度并提交处理结果。待确认工单为下一史诗的确认关闭和失败退回提供输入。
