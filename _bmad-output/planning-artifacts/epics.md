# 实验室报修跟踪 · 史诗与故事

## 概览

本稿按现有 PRD 和架构草稿拆分，沿用单机 Web 假设。工单模型和写入服务由三个史诗共用。每个史诗对应可单独演示的交付点，依次为报修可查询、处理进展可见、试打验收可闭环。 [PRD](prds/prd-BMAD-Codex-练习-20261108-2026-11-09/prd.md) · [架构方案与 ADR](architecture/architecture-BMAD-Codex-练习-20261108-2026-11-09/architecture.md) · [架构约束](architecture/architecture-BMAD-Codex-练习-20261108-2026-11-09/ARCHITECTURE-SPINE.md)

## 需求清单

### 功能需求

| 编号 | 需求 |
| --- | --- |
| FR-1 | 成员填写设备、位置和故障描述，提交后生成「待接单」工单并记录报修人。 |
| FR-2 | 报修人能查看自己提交的工单。列表显示设备、状态、跟进人和工单最近更新时间。 |
| FR-3 | 负责人可分别查看待接单工单和自己接下的工单，列表字段与 FR-2 一致。 |
| FR-4 | 按权限查看工单详情。详情展示设备、故障、状态、跟进人、工单最近更新时间及处理历史。有进度时，显示最新进度及其记录时间。 |
| FR-5 | 负责人接单后成为跟进人，工单进入「处理中」。 |
| FR-6 | 跟进人可在「处理中」多次追加进度，保留每条内容和时间。 |
| FR-7 | 跟进人填写处理结果并提交验收，工单进入「待确认」。 |
| FR-8 | 仅该单报修人可在「待确认」时确认修好，将工单关闭。 |
| FR-9 | 仅该单报修人可在「待确认」时填写原因并退回。沿用原工单和原负责人，保留历史，并允许再次提交验收。 |

### 非功能需求

| 编号 | 需求 |
| --- | --- |
| NFR-1 | 同一轮验收只允许一个结果。并发关闭和退回时恰好一个成功，成功事件和工单最终状态一致。 |
| NFR-2 | 服务端按身份、归属和状态保护工单。越权读取无数据返回，越权写入不改变工单或历史。 |

### 架构约束

- **ADR-001 / AD-1** 以 Django 官方 `startproject` 为起点，服务端渲染。页面入口调用统一的工单查询或写入服务。
- **ADR-002 / AD-2** 使用单机 SQLite 文件和短 `IMMEDIATE` 写事务，并发集成测试使用独立连接。区分版本冲突与锁超时。
- **ADR-003 / AD-3** 已有工单写入必须验证预期状态及版本。成功时版本加一，旧版本不得作用于当前工单。
- **ADR-004 / AD-4** 用服务端会话和负责人组确定身份及角色，统一执行可见性和对象权限。
- **ADR-005 / AD-5** 工单变更和追加事件在同一事务内提交，详情按版本展示历史。

### UX 输入

本轮依据 PRD 的用户动作和验收路径拆分。练习目录中暂无单独的 UX 设计文档。

### 需求覆盖

| 需求 | 负责交付的史诗 |
| --- | --- |
| FR-1、FR-2、FR-4 | 史诗 1 交付报修与基础详情。史诗 2、3 随新动作扩展详情中的处理历史。 |
| FR-3、FR-5、FR-6、FR-7 | 史诗 2 交付接单、处理和提交验收。 |

| NFR-2 | 三个史诗随各自查询和写入功能交付权限校验。 |

## 史诗清单

1. **报修与查询**。成员提交公共设备故障后能查回原工单。可在尚未有人接单时独立验收。
2. **接单与跟进**。负责人能找到待接单工单、接单、记录进展并提交验收。依赖史诗 1 的工单和基础详情，可验收到「待确认」。
3. **验收与关闭**。报修人能试打确认，或填写原因退回原负责人再试。依赖史诗 2 的待确认工单，交付两条完整路径及并发验收保护。

## Epic 1: 报修与查询

实验室成员提交公共设备故障后，可以在自己的列表查回工单。

### Story 1.1: 从 Django 骨架启动并登录

作为实验室成员，我希望用自己的账号进入报修应用，以便工单能关联到实际报修人。

**追溯**　NFR-2，ADR-001、ADR-002、ADR-004。**依赖**　无。

**实现约束**　用官方 `startproject` 初始化。此故事只准备登录所需的配置、认证表及演示账号。工单和事件表随 1.2 引入。

**验收标准**

- **AC-1.1a** 给定空白本地数据目录，当评审者按启动步骤初始化数据库和演示账号并启动 Django 应用时，登录页返回可用页面，重启后仍可使用已创建的账号。
- **AC-1.1b** 给定普通成员和负责人各一个账号，当两者分别登录时，服务端会话分别解析为对应账号，且只有负责人账号属于负责人组。
- **AC-1.1c** 给定未登录会话，当直接访问受保护的应用入口时，返回登录提示或跳转登录页，响应中无工单数据。

### Story 1.2: 提交公共设备报修

作为成员，我希望提交设备名称、位置和故障描述，以便留下可跟踪的工单。

**追溯**　FR-1、NFR-2，ADR-001、ADR-004、ADR-005。**依赖**　1.1。

**验收标准**

- **AC-1.2a** 给定已登录成员，当提交设备「公共打印机」、位置「实验室公共区」、故障描述「卡纸，无法打印」时，新增恰好一张工单，三项字段与输入一致，报修人是当前会话成员，状态为「待接单」，跟进人为空，并记录创建事件和工单更新时间。
- **AC-1.2b** 给定成员提交缺少设备名称、位置或故障描述的表单，当逐项验证时，每次响应均指出缺失字段，工单数和创建事件数均不增加。

### Story 1.3: 查找我提交的工单

作为报修人，我希望看到自己提交的工单列表，以便快速找到打印机报修和当前状态。

**追溯**　FR-2、NFR-2，ADR-001、ADR-004。**依赖**　1.2。

**验收标准**

- **AC-1.3a** 给定成员甲和乙各提交一张工单，当甲打开自己的工单列表时，结果包含甲的工单编号，且不包含乙的工单编号。
- **AC-1.3b** 给定甲的工单处于「待接单」，当甲查看列表项时，设备、状态和工单最近更新时间与工单记录一致，跟进人显示「尚无跟进人」。

### Story 1.4: 查看单张工单及保护详情入口

作为报修人，我希望打开工单核对报修信息，以便确认看到的是自己提交的故障。

**追溯**　FR-4、NFR-2，ADR-001、ADR-004。**依赖**　1.2、1.3。

**验收标准**

- **AC-1.4a** 给定一张由甲提交的待接单工单，当甲从自己的列表打开详情时，工单编号、设备、位置、故障描述、状态和工单最近更新时间与存储记录一致。
- **AC-1.4b** 给定乙是无关普通成员且已知该工单编号，当乙直接请求详情时，请求被拒绝，响应中无工单字段和历史内容。

## Epic 2: 接单与跟进

负责人能找到待处理工单、记录进展，并交给报修人验收。报修人能看到谁在跟进和最新处理进展。

### Story 2.1: 查看待接单和本人接下的工单

作为负责人，我希望分开看待接单工单和我的工单，以便找到当前需要处理的任务。

**追溯**　FR-3、FR-4、NFR-2，ADR-001、ADR-004。**依赖**　1.2、1.4。

**验收标准**

- **AC-2.1a** 给定测试数据包含待接单工单、当前负责人接下的工单、其他负责人接下且与当前负责人无报修归属的工单，当当前负责人分别打开两个列表时，待接单列表只显示第一类，本人接下列表只显示第二类。列表项显示设备、状态、跟进人和工单最近更新时间。
- **AC-2.1b** 给定同一批数据，当当前负责人直接请求三类工单详情时，前两类返回对应工单信息，第三类被拒绝且无工单数据返回。

### Story 2.2: 接下待接单工单

作为负责人，我希望接下待接单工单，以便报修人能看到谁在跟进。

**追溯**　FR-3 至 FR-5、NFR-2，ADR-002 至 ADR-005。**依赖**　2.1。

**验收标准**

- **AC-2.2a** 给定待接单工单和其当前版本，当负责人甲提交接单时，工单进入「处理中」，跟进人为甲，版本加一并新增一条接单事件。刷新后，待接单列表移除该单，甲的工单列表和报修人详情显示甲。
- **AC-2.2b** 给定已被甲接下的工单，当负责人乙使用接单前的版本提交接单时，请求被拒绝，跟进人仍为甲，工单版本、更新时间和事件数均与请求前相同。
- **AC-2.2c** 给定另一张待接单工单，当普通成员直接提交接单请求时，请求被拒绝，工单仍待接单且无接单事件。

### Story 2.3: 追加处理进度

作为跟进人，我希望能多次记录处理进度，以便报修人知道工作推进到了哪一步。

**追溯**　FR-4、FR-6、NFR-2，ADR-003 至 ADR-005。**依赖**　2.2。

**验收标准**

- **AC-2.3a** 给定一张由甲跟进的「处理中」工单，当甲用每次提交时的当前版本先后记录「已取出卡纸」和「正在检查进纸口」时，工单状态保持「处理中」，版本共加二，历史新增两条有操作者、内容和服务端时间的进度事件。
- **AC-2.3b** 给定上述两次更新已提交，当报修人打开工单详情时，历史按版本顺序显示两条进度，最新进度显示第二条的内容及记录时间。
- **AC-2.3c** 给定乙是另一位负责人，当乙直接请求追加进度时，请求被拒绝，原状态、跟进人、版本、更新时间及历史均保持原值。

### Story 2.4: 填写结果并提交验收

作为跟进人，我希望提交处理结果供报修人试打，以便报修人知道何时可以验证修复。

**追溯**　FR-4、FR-7，ADR-003 至 ADR-005。**依赖**　2.2、2.3。

**验收标准**

- **AC-2.4a** 给定当前跟进人的「处理中」工单，当其用当前版本提交处理结果「已清理进纸口，请试打一页」时，工单进入「待确认」，版本加一，详情显示该处理结果，之前的进度记录仍可查。
- **AC-2.4b** 给定当前跟进人的另一张「处理中」工单，当其提交空白处理结果时，请求被拒绝，状态和版本保持原值，未新增提交验收事件。

## Epic 3: 验收与关闭

报修人完成试打，确认关闭或将问题退回原负责人。每轮验收只产生一个结果。

### Story 3.1: 试打成功后关闭

作为报修人，我希望在试打正常后关闭原工单，以便确认设备可以恢复使用。

**追溯**　FR-4、FR-8、NFR-2，ADR-003 至 ADR-005。**依赖**　2.4。

**验收标准**

- **AC-3.1a** 给定打印机卡纸工单已进入「待确认」，当报修人试打正常并用当前版本确认时，原工单进入「已关闭」，版本加一，新增一条关闭事件，原进度和处理结果仍可查。
- **AC-3.1b** 给定另一张仍待确认的工单，当跟进人直接提交关闭请求时，请求被拒绝，工单的状态、版本、更新时间和事件数均与请求前一致。
- **AC-3.1c** 给定一张已关闭工单，当报修人用其当前版本再次提交关闭时，请求被拒绝，关闭事件数保持为一。

### Story 3.2: 试打失败后退回原负责人

作为报修人，我希望填写失败原因并退回原工单，以便原负责人继续处理并再次交付验收。

**追溯**　FR-4、FR-6 至 FR-9、NFR-2，ADR-003 至 ADR-005。**依赖**　2.4、3.1。

**验收标准**

- **AC-3.2a** 给定一张「待确认」工单，当报修人提交缺失或仅含空白字符的退回原因时，请求被拒绝，工单仍待确认，版本、更新时间和事件数保持原值。
- **AC-3.2b** 给定同一工单，当报修人用当前版本提交「试打仍卡纸」时，状态回到「处理中」，工单编号与跟进人均保持原值，版本加一，原负责人能查到新增的退回原因和之前的处理记录。
- **AC-3.2c** 给定工单已退回，当原负责人追加进度并再次提交处理结果，报修人复测通过后确认关闭时，同一工单进入「已关闭」，两轮处理结果、一次退回原因和关闭事件均可查。
- **AC-3.2d** 给定另一张「待确认」工单，当非报修人直接提交有效退回原因时，请求被拒绝，未新增退回事件，工单仍处于「待确认」。

### Story 3.3: 保护同一轮验收的唯一结果

作为报修人，我希望同时发出的关闭和退回只生效一次，以便工单有明确的最终结果。

**追溯**　FR-8、FR-9、NFR-1，ADR-002、ADR-003、ADR-005。**依赖**　3.1、3.2。

**验收标准**

- **AC-3.3a** 给定本地文件数据库中的一张「待确认」工单，当同一报修人从两个独立会话、由两个独立数据库连接并发提交同一版本的关闭和有效退回时，恰好一个请求成功，另一个返回状态或版本冲突提示，版本只加一，且恰好新增一条验收结果事件。
- **AC-3.3b** 给定 AC-3.3a 的操作，分别验证关闭先提交成功和退回先提交成功的情形。重新读取工单时，关闭获胜对应「已关闭」及唯一的关闭事件，退回获胜对应「处理中」、原跟进人及包含原因的唯一退回事件。败方动作无事件。

### Story 3.4: 隔离旧请求与写入失败

作为报修人，我希望旧验收页面和失败写入都不会改变当前验收结果，以便复测时仍能信任工单历史。

**追溯**　FR-7 至 FR-9、NFR-1，ADR-002、ADR-003、ADR-005。**依赖**　3.1、3.2、3.3。

**验收标准**

- **AC-3.4a** 给定报修人保留第一轮「待确认」页面，且工单已退回并再次提交验收，当报修人分别用第一轮页面的版本提交关闭和有效退回时，两次请求均被拒绝，第二轮仍为「待确认」，版本、更新时间和事件数均与请求前相同。
- **AC-3.4b** 给定当前待确认工单，当测试在条件更新成功后、追加事件时注入写入异常时，请求未返回成功。用另一连接重新读取，状态、版本、更新时间和历史与请求前一致。
- **AC-3.4c** 给定另一数据库连接持续持有写锁直至关闭请求的锁等待超时，当报修人提交当前版本的关闭时，应用报告暂时不可用。释放锁后重新查询，工单仍待确认且未新增关闭事件。

## 第一版端到端验收

两条路径各使用一张新建的「公共打印机卡纸」工单。共同前置是提交报修、负责人接单并追加进度、报修人查到跟进人与最新进度时间、负责人填写处理结果后提交验收（1.2、2.2–2.4）。

| 路径 | 最终断言 |
| --- | --- |
| 试打成功 | 报修人确认后，原工单为「已关闭」，仍可查看进度和处理结果（AC-3.1a）。 |
| 试打失败、退回、复测通过 | 原工单先退回「处理中」，原因可查，原负责人再次提交验收后由报修人关闭。工单编号、跟进人及先前记录均保留（AC-3.2b、AC-3.2c）。 |
