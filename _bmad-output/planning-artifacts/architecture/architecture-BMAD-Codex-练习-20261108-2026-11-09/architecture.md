# 实验室报修跟踪 · 架构方案与 ADR

第一版提议采用 Django 服务端渲染、分层单体和本机 SQLite。以下五条 ADR 记录当前的建议及暂缓采用其他方案的理由，均待确认。规则细节和依赖方向见[架构约束](ARCHITECTURE-SPINE.md)，需求编号来自[PRD 草稿](../../prds/prd-BMAD-Codex-练习-20261108-2026-11-09/prd.md)。

| ADR | 当前建议 | 本轮暂缓采用的备选方案与理由 |
| --- | --- | --- |
| ADR-001 · 应用结构 | 采用服务端渲染的分层单体，页面与工单服务分层（AD-1）。 | 前后端独立部署。第一版主要是列表、详情和表单，独立部署会增加 API 契约、会话配置及两套启动流程。 |
| ADR-002 · 持久化 | 使用本机 SQLite 文件和短写事务（AD-2）。 | 独立 PostgreSQL 服务。它提供更细粒度的并发控制，也会增加演示机上的服务初始化和配置。若 SQLite 在并发验收中无法满足要求，重新比较。 |
| ADR-003 · 状态一致性 | 使用工单状态和版本的条件更新，关闭和退回竞争同一个版本（AD-3）。 | 只按当前状态更新。工单退回后能再次进入「待确认」，上轮页面的迟到请求可能错误地关闭或退回新一轮验收。 |
| ADR-004 · 工单授权 | 使用服务端会话和负责人组，在工单服务统一校验对象权限（AD-4）。 | 页面各自隐藏操作按钮。用户仍可以绕过页面直接请求详情或写入，无法满足 NFR-2。 |
| ADR-005 · 处理历史 | 追加式工单事件与状态更新在同一事务提交（AD-5）。 | 只保留一个可覆盖的进度或处理结果字段。重复提交验收后会丢失之前的处理结果和退回原因，无法验收 FR-9。 |

## 方案验收

| 检查 | 预期结果 | 追溯 |
| --- | --- | --- |
| 打印机卡纸的试打成功与失败退回 | 两条路径都能查到跟进人及最近进度。退回后保留原单、原负责人和先前记录。 | FR-1 至 FR-9 |
| 两个独立连接同时发起关闭和退回 | 恰有一次成功。另一个报告冲突。工单状态与唯一成功事件一致。 | NFR-1，ADR-002、003、005 |
| 旧验收页面在新一轮提交后发出请求 | 拒绝旧版本请求，当前验收轮次和历史保持一致。 | NFR-1，ADR-003 |
| 模拟历史写入异常 | 当前状态和历史一起回滚，前端未收到操作成功的结果。 | NFR-1，ADR-005 |
| 越权访问列表、详情和写入 | 无关成员看不到工单，非跟进人无法更新进度，跟进人无法代报修人关闭。 | NFR-2，ADR-004 |

上述检查待实现后执行。当前交付假设为单机 Web 演示。评审机环境、账号初始化方式和依赖补丁版本将在建立项目骨架时确认。
